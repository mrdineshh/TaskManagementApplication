# 09 — Terraform / Infrastructure as Code

Read `08-INFRA-DEPLOYMENT.md` first — this document is the detailed companion
to that one, covering specifically how the GCP infrastructure is defined,
organized, and changed via Terraform. It's kept separate so the team can pick
up and modify infrastructure independently of the broader deployment
narrative in `08`.

---

## 1. Why Terraform, and where it lives **[Fixed]**

- All GCP resources described in `08-INFRA-DEPLOYMENT.md` §2 (Cloud Run,
  Cloud SQL, Cloud Storage, Cloud Scheduler/Tasks, Secret Manager, Artifact
  Registry, IAM bindings, Firebase project config) are defined as Terraform
  code — nothing is clicked into existence manually in the GCP Console for
  environments that Terraform manages, except the handful of one-time manual
  account/billing steps listed in `08-INFRA-DEPLOYMENT.md` §9, which are
  outside what Terraform (or any code) can provision.
- Lives at `infra/` in the monorepo root (per `01-ARCHITECTURE.md` §4),
  **alongside**, not inside, `apps/` or `packages/` — infra changes are
  reviewed via the same PR process as application code, but are a distinct
  concern.

## 2. Module structure **[Default]**

```
infra/
├── modules/
│   ├── cloud-run-service/       # reusable: Cloud Run service + IAM + domain mapping
│   ├── cloud-sql-instance/       # reusable: Postgres instance + database + user
│   ├── storage-bucket/            # reusable: bucket + lifecycle rules + IAM
│   ├── scheduler-job/              # reusable: Cloud Scheduler job + target
│   ├── secret/                      # reusable: Secret Manager secret + IAM binding
│   └── networking/                   # reusable: any shared networking config
├── environments/
│   ├── dev/
│   │   ├── main.tf                  # composes modules for the dev project
│   │   ├── variables.tf
│   │   ├── terraform.tfvars          # dev-specific values (project id, sizing, etc.)
│   │   └── backend.tf                 # remote state config, see §3
│   ├── staging/
│   │   └── (same structure)
│   └── prod/
│       └── (same structure)
└── README.md                          # quickstart: how to plan/apply, see §5
```

- **Why modules + environments, not one flat config:** the three environments
  (`08-INFRA-DEPLOYMENT.md` §1) share the same *shape* of infrastructure but
  differ in sizing, instance counts, and a few settings (e.g. Cloud Run
  min-instances = 0 in dev, 1 in prod). Modules capture the shared shape once;
  each environment's `main.tf` composes those modules with environment-
  specific variables — this is what lets prod be deployed with confidence
  that it's structurally identical to what was tested in staging, differing
  only in intentional, reviewable ways (sizing, not architecture).

## 3. State management **[Fixed]**

- **Remote state**, stored in a dedicated **Cloud Storage bucket** (one per
  environment, or one bucket with per-environment prefixes — either is
  acceptable; **Default: one bucket per environment**, matching the
  project-per-environment isolation principle in `08-INFRA-DEPLOYMENT.md`
  §1).
- **State locking** enabled (GCS backend supports this natively) to prevent
  concurrent `terraform apply` runs from corrupting state — important once
  more than one person or the CI pipeline might run Terraform.
- **State bucket itself** is one of the few things provisioned manually
  (or via a small bootstrap script) before the main Terraform config can run,
  since Terraform needs somewhere to store state before it can manage its own
  backend. This bootstrap step is documented explicitly in the `infra/README.md`
  quickstart (§5) so it isn't a mystery step the team forgets how to repeat.

## 4. Variables & secrets **[Fixed]**

- Environment-specific, non-secret values (project ID, region, instance
  sizing, min/max Cloud Run instances) live in each environment's
  `terraform.tfvars`, committed to source control — these are configuration,
  not secrets.
- **Actual secrets** (DB passwords, OAuth client secret, API keys) are **never
  put in `.tfvars` or any committed file.** Terraform creates the Secret
  Manager *resources*, but the secret *values* are either:
  - Generated by Terraform itself where possible (e.g. a random DB password
    via the `random_password` provider, stored directly into Secret Manager),
    or
  - Supplied at apply-time via environment variables /
    `-var` flags sourced from a secure location (e.g. the CI pipeline's own
    secret store), never written to disk in plaintext.
- This keeps the repository safe to be broadly readable by the team (per the
  configurability/transparency spirit of this whole project) without ever
  exposing real credentials.

## 5. Workflow: how the team applies changes **[Default]**

Documented in full in `infra/README.md` (to be created alongside the
Terraform code itself), summarized here:

```
1. Make changes to the relevant module or environment config on a branch.
2. Run `terraform plan` against the target environment — review the diff
   carefully, especially for staging/prod (what will be created, changed, or
   destroyed).
3. Open a PR with the plan output included/attached for review — infra
   changes are reviewed like any other code change, not applied ad hoc.
4. On merge:
   - dev: Terraform applies automatically via the CI pipeline
     (`08-INFRA-DEPLOYMENT.md` §4).
   - staging/prod: Terraform apply requires a manual approval step in the
     pipeline (same promotion gate philosophy as the application deploy
     pipeline) — infrastructure changes to prod are never fully automatic.
```

- **Destructive changes** (anything that would destroy/recreate a stateful
  resource like Cloud SQL) should be called out explicitly in the PR
  description — `terraform plan` will show this, but it's worth a human
  explicitly acknowledging it before merge, given how costly an accidental
  database recreation would be.

## 6. What Terraform does *not* manage **[Fixed — matches `08-INFRA-DEPLOYMENT.md` §9]**

For clarity, restating what stays manual and why, since it's easy to assume
"infrastructure as code" means everything is automated:

- GCP billing account setup and linking.
- Google OAuth client / Firebase project creation (can partially be automated
  via the Firebase Management API/Terraform's `google-beta` provider in some
  cases — worth the build agent investigating at build time, but not assumed
  here as fully automatable given org-verification steps that may require
  manual console interaction).
- Apple Developer / Google Play Console account setup.
- Domain registrar configuration (not applicable yet, per
  `08-INFRA-DEPLOYMENT.md` §7 — default GCP URLs at launch).
- Transactional email provider account + domain verification records.
