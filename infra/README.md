# Infrastructure — Terraform quickstart

This directory provisions everything described in `docs/08-INFRA-DEPLOYMENT.md` and
`docs/09-TERRAFORM-IAC.md`. It has **not been applied** — no real GCP project exists yet.
Everything below is ready to run once GCP access is provided.

```
infra/
├── modules/                  # reusable building blocks
│   ├── cloud-run-service/    # API service + IAM + optional Cloud SQL connection
│   ├── cloud-sql-instance/   # Postgres instance + db + user + connection-string secret
│   ├── storage-bucket/       # bucket + lifecycle rule (attachments/exports)
│   ├── scheduler-job/        # Cloud Scheduler job -> authenticated Cloud Run call
│   ├── secret/                # Secret Manager secret + accessor IAM binding
│   └── networking/            # optional VPC connector (off by default — not needed at v1 scale)
└── environments/
    ├── dev/
    ├── staging/
    └── prod/
```

Each environment composes the same modules with different sizing (`terraform.tfvars`) —
structurally identical infrastructure, differing only in reviewable ways (instance size,
min/max Cloud Run instances, HA), per `docs/09-TERRAFORM-IAC.md` §2.

## 0. What Terraform does *not* provision

These require a human with account/billing authority and cannot be created by Terraform
(or any build agent) — see `docs/08-INFRA-DEPLOYMENT.md` §9:

- GCP billing account, linked to the three projects
- The three GCP projects themselves (`econz-taskapp-dev/staging/prod`) and enabling their APIs
  (Cloud Run, Cloud SQL, Secret Manager, Cloud KMS, Cloud Scheduler, Artifact Registry, Cloud Build)
- Google OAuth client / Firebase project (for Sign-In with Google)
- Apple Developer + Google Play Console accounts (mobile distribution)
- GitHub repo access with permission to configure Cloud Build triggers

**Ask the user for these when you reach this step** — they've indicated they're ready to
provide them on request, per `docs/10-OPEN-DECISIONS.md`.

## 1. One-time bootstrap (per environment)

The Terraform state bucket must exist before Terraform can manage its own backend, and
Terraform itself needs a service account with the right (least-privilege, not Owner) roles.
Run `environments/<env>/bootstrap-terraform-sa.sh` from a machine authenticated as a project
owner/editor — this is the human-authority step `docs/08-INFRA-DEPLOYMENT.md` §9 calls out,
not something Terraform or a build agent does for itself:

```bash
cd infra/environments/dev
PROJECT_ID=econz-taskapp-dev REGION=us-central1 ./bootstrap-terraform-sa.sh
```

This enables the required APIs, creates a `terraform-dev` service account scoped to just the
roles this config touches (IAM, KMS, Secret Manager, Cloud SQL, Storage, Cloud Run), writes
its key to `./terraform-dev-key.json` (gitignored — never commit it), and creates + versions
the `gs://<project-id>-tfstate` state bucket. Delete or rotate the key once you're done with
it (`gcloud iam service-accounts keys delete`) — a standing key is a standing risk.

## 2. Apply an environment

```bash
cd infra/environments/dev
cp terraform.tfvars.example terraform.tfvars   # edit non-secret values
terraform init
terraform plan -var="google_oauth_client_secret=$GOOGLE_OAUTH_CLIENT_SECRET"
terraform apply -var="google_oauth_client_secret=$GOOGLE_OAUTH_CLIENT_SECRET"
```

- Never put actual secret values in `terraform.tfvars` — pass them via `-var` or a CI
  secret store, per `docs/09-TERRAFORM-IAC.md` §4. The DB password is generated by
  Terraform itself (`random_password`) and never needs to be supplied.
- `staging` and `prod` should go through the CI pipeline's manual-approval gate
  (`docs/08-INFRA-DEPLOYMENT.md` §4), not be applied ad hoc from a laptop, once CI exists.

## 3. What's deliberately not built yet

- **Cloud CDN / custom domain**: the web static bucket is provisioned, but fronting it
  with an HTTPS Load Balancer + Cloud CDN is skipped until a custom domain is actually
  wanted — `docs/08-INFRA-DEPLOYMENT.md` §7 confirms launch on default GCP URLs.
- **Cloud Scheduler jobs**: the `scheduler-job` module is ready, but no jobs are wired up
  yet since the v1 backend doesn't have any scheduled endpoints to call (SLA checks,
  report aggregation, etc. are v1.1/v1.2 features per `docs/05-FEATURES.md`).
- **Cloud Build triggers / CI pipeline**: `docs/08-INFRA-DEPLOYMENT.md` §4 describes the
  pipeline, but the trigger config itself isn't in this directory yet — add a
  `cloudbuild.yaml` at the repo root plus trigger resources once GitHub access is granted.

## 4. Validating without a real GCP project

`terraform fmt -recursive -check` and `terraform validate` both pass against every
environment in this repo (verified against the real `hashicorp/google` v6 provider
schema, offline via a local provider mirror, since this sandboxed build environment's
network policy doesn't allow reaching `registry.terraform.io` directly). `terraform plan`
requires real GCP credentials and a live project, so it hasn't been run.
